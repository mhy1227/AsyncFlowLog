现有行为（源码证据）

- 服务宕机/关闭：AsyncLogServiceImpl 在 @PreDestroy 中调用 shutdown()，先把 running 置 false，再停掉 ConsumerPool（src/main/java/com/asyncflow/log/service/impl/AsyncLogServiceImpl.java:75-80）。消费者线程在循环里捕获          
  InterruptedException，会优雅退出（src/main/java/com/asyncflow/log/consumer/ThreadPoolConsumer.java:226-252）。但若是异常崩溃，队列里尚未消费的日志依旧会丢失——当前实现没有 WAL 或持久化。
- 队列满：submitEvent 只调用 eventQueue.offer(event)，返回 false 时写 warning 日志提醒“队列满丢弃日志”（src/main/java/com/asyncflow/log/service/impl/AsyncLogServiceImpl.java:241-249）。没有自动重试或阻塞等待，属于“及时发现、主
  动丢弃”策略。
- 写入失败：ThreadPoolConsumer 在执行写入时若抛出异常，会调用 eventHandler.handleException(event, e)；而默认的 LogEventHandler.handleException 会统计错误并尝试再写一次（src/main/java/com/asyncflow/log/appender/                
  LogEventHandler.java:108-119）。如果再次失败，就只记录日志，不再重复。
- 幂等信息：LogEventDTO 自带 logId （UUID），如果后续实现重放/重试，可以利用它做幂等判定（src/main/java/com/asyncflow/log/model/event/LogEventDTO.java:16-33）。

可以强化的策略（面试回答时重点）

1. 宕机场景
    - 配置 AsyncLogService.flush() 在停机流程中主动刷盘，把队列清空后再关闭线程池。
    - 引入本地 WAL/持久化缓冲（先写临时文件再写正式日志），重启时补写。
    - 更进一步，将 LogAppender 换成 Kafka/RabbitMQ 等具备持久化与确认机制的后端。
2. 队列满/洪峰
    - 可在 submitEvent 中增加退避策略：例如失败后短暂阻塞 eventQueue.offer(event, timeout)、动态扩容队列、增加消费者线程数。
    - 当持续失败时触发降级：切换到同步写入（直接调用 appender.append）、记录简化日志、或将重要日志写到备用通道。
3. 写入失败 & 重试
    - handleException 目前只重试一次，可改成「固定次数重试 + 回落到 WAL/MQ + 告警」。
    - 搭配 Metrics 监控错误率、丢弃数，到达阈值报警。
4. 幂等/重放
    - logId 可作为消息 ID，重放时先检查是否已经落地，避免重复。
    - 若使用 MQ，消费者端可以利用这个 ID 做去重。
